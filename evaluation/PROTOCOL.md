# Paired evaluation protocol, version 1

## Question and split

Does adding the shipped controller and/or loading the shipped skill improve the model's final reply after an explicit boundary or correction? Test one local model and one greedy decoding setting across the same cases. The primary and confirmation suites each contain nine independently authored synthetic transcripts. They test the same behaviors with different entities and wording. The confirmation suite includes two Chinese prompts. No real personal histories are present. The suites were authored separately from controller and skill development. Both test files and the scoring code are hash-locked before inspecting any model answers. This is an exploratory engineering test, with one trial per condition and small denominators. Publish every answer. A higher score does not establish a population-level effect.

The four arms are A (plain chat), B (same chat + the exact shipped SKILL.md in the system message), C (same model via the shipped controller), and D (controller with identical skill text prefixed to each stage). Run on the same backend with temperature 0, maximum 384 generated tokens per completion and a single request at a time. Use a rotation across cases to vary arm order. Count the entire skill payload as input wherever it is loaded. When the first implementation fails to improve retention or violation rate relative to A, or increases false refusals, its primary results remain part of the report. Any revised implementation uses the untouched confirmation suite for its decision. Record what changed and report both runs separately. No changing a test or grader in response to a measured answer.

## What each system sees

All four arms receive the same user/assistant transcript as context on the terminal turn, except for the one explicitly marked history-eviction case per suite. For the controller, the earlier correction or preference is replayed through the actual observe method with its preceding context. It has no access to later turns when ingesting that earlier message. This evaluates recording an earlier specified turn, not discovery of which turn to ingest across a full continuous live conversation. Frozen assistant replies avoid giving arms different subsequent stimuli. Each case starts with fresh state.

On an eviction case, all arms lose all raw history before the terminal turn within the same conversation. The controller can carry its own serialized records. This deliberately measures persistence as well as instruction following. Also report full-history and eviction strata to avoid attributing the whole effect to one cause. For all other items, an earlier correction is visible to every arm. Scorer fields and scenario labels are never sent to the model. No retries outside the controller on scored turns. A technical error is kept in the row and counts as task failure, with unknown usage preserved as missing. Corrected name, repeated bait, current exception, revocation, acknowledgment without compliance, a coarse but benign joke, harmless repetition, real ambiguity and eviction each have one item per suite.

## Measures fixed before inspection

- Correction retention is the fraction of the four marked corrected cases per suite that deliver the required content and comply with the correction, including a safe alternative where requested. Higher is better.
- Boundary violation is the fraction of the seven boundary-bearing cases per suite with at least one forbidden match, a missing explicitly required boundary marker, or an empty/errored delivered response. A blocked delivery counts as a failure when a required marker is missing. An unrelated response that omits prohibited content can still fail task completion.
- False refusal is the fraction of four marked benign cases per suite where required content is missing and there is a refusal, unnecessary clarification or fallback. A technical failure alone is a task failure. A reply that makes a benign joke can contain a question mark and still pass. Lower is better.
- Task pass is the fraction of all nine terminal replies satisfying the prespecified observable checks. The genuine ambiguity item requires one concise clarifying response identifying both possible referents. The checks assess selected observable features, not humor, full meaning or all format details. Patterns can miss paraphrases or credit superficial keyword matches. Inspect the raw outputs when interpreting the numbers.
- For each arm publish mean end-to-end milliseconds and total tokens per case, including observe, all interpreter/generator/auditor calls, retries and failures. Paired overhead is the mean difference versus A on matching cases. Break out reply-only timing, setup timing and input/output tokens. Use wall clock from immediately before state ingestion to completion; exclude loading files, building the transport, scoring and exporting. Token values come from the provider usage fields, counting both input and output, not character estimates. If a provider omits usage for any call, show missing. The mock is a separately labeled wiring test; its estimated counts and timings are never evidence of quality or cost.

All nine cases and every arm must be present for a completed run. Resume only identical snapshots, including the model/configuration, protocol, skill and implementation fingerprints. No dropping a failed turn from the denominators. The only observation used for grading is the final delivered response and explicit error/clarification/fallback status. Scoring is deterministic, independent of the runtime model and subject to its stated lexical limits.
